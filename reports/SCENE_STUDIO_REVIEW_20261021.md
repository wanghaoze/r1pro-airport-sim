## 结论

**这个项目已经具备实验工作台的主要组件，但还不是可以独立交接、让普通用户完成全流程的成熟平台。当前最应优先处理的是源码和发布版本闭合、场景到训练的流程缺口，以及状态显示的可信度。**

网站能编辑场景草稿、组织登记数据、提交训练与评测、展示结果和帮助文档；这些有真实实现，不能简单判断为“只有界面”。不过，编辑后的场景不会直接成为训练数据，策略评估也仍使用登记初态。网站能力与机器人模型能力应分别验收。

## 1. 项目是怎样工作的

前端是 React/TypeScript 与 Three.js；云端通过 Sites/Workers、D1 和对象存储提供页面、草稿、队列与下载；工作站版使用 Node HTTP 服务、SQLite 和本地文件适配同一批 API。Python worker 主动轮询任务，再调用独立的训练、MSE、Isaac 仿真与模型适配程序。

```mermaid
flowchart LR
  A[场景编辑与版本保存] --> B[Sync to GPU：场景草稿]
  B --> C[维护者：适配、预检、原生采集、资格审核]
  C --> D[导出、冻结、登记新数据集]
  D --> E[网页选择已有数据并提交训练]
  E --> F[GPU 队列与独立运行目录]
  F --> G[检查点]
  G --> H[MSE / 登记初态策略评估]
  H --> I[回执、报告与视频]
```

其中 B→D 是当前主要人工环节。网页固定底盘 Pick/Place 分支与项目三动作任务不是同一个范围；不能把本网站的两动作评测称为 Pick/Place/Flush 整体任务验收。

值得保留的设计包括：服务端字段与动作合同校验、revision 乐观并发检查、按用户隔离草稿、任务请求去重、来源域与 split 标记，以及“流程完成”和“模型成功”的分离。

## 2. 已确认的主要问题

### 2.1 网站源码与可重建交付缺失

当前仓库没有 `apps/scene-agent/`，`git ls-files apps/*` 也没有跟踪项，但 README、网站手册及两份 studio 测试都依赖该目录。现有网站代码主要存在于 `exports/` 压缩包中。

本轮解开 `scene_studio_live_policy_20261019_v5.zip` 后实际运行 `npm run build`，在加载 `scripts/run-framework.mjs` 时即报 `MODULE_NOT_FOUND`。四份网站 ZIP 和一份 Sites TAR 都没有这个脚本，也没有 `db/schema.ts`；因此文档描述的标准开发/云构建路径并不完整。

**边界：这不等于离线预构建页面不能运行。** 独立临时数据库下直接启动包内 `offline-dist/server.mjs`，首页、health、bootstrap 均返回 200。未启动 worker。尚未执行 `npm ci` 或验证 `node offline/build.mjs` 的离线重建，不能把标准 build 的失败扩大成所有构建方式都失败。

建议：恢复可跟踪的主源码目录，区分“完整开发源码”“离线可运行包”“GPU release”，提供各自清单与构建入口。在全新目录验证安装、类型检查、构建、启动和基础 API，之后才将包标为可交接。

证据：[导出包](../exports/scene_studio_live_policy_20261019_v5.zip)、[审计清单](../runs/site_audit_20261021/audit_evidence.json)、[本地直连验证](../runs/site_audit_20261021/direct_probe.json)。依赖路径见 `tests/test_studio_training.py:13` 和 `tests/test_studio_auto_evaluation.py:6`。

### 2.2 发布版本分散，旧包保留已知故障路径

本轮 Sites 查询确认云端最新为 **v12**，commit `b37865c1308db6795a81e2ce8474310f0122667d`。当前工作树最新离线导出包为文件名中的 **v5**，Sites 导出为 **v8**；项目记录则描述工作站修复已到 **v13**。这些编号属于不同发布线，不能只比较数字；问题在于没有一份统一清单说明代码、构建产物、前端、worker 和模型运行层的对应关系。

v5 导出仍存在以下旧逻辑：

- `lib/server.ts:12` 对 worker JSON 仍统一使用 250,000 字符限制；后续项目记录已提到大快照导致 HTTP 413 并修复。
- `offline/supervisor.py:46` 任一子进程退出即抛错，随后 `finally` 结束所有子进程；bridge 故障会连带关闭网页。后续记录称已隔离。
- `app/PolicyEvaluation.tsx:10` 自动选取最新历史运行；后续记录要求刷新回到原始预览。
- `lib/training.ts:36` 先检查客户端 framesPerAction，再验证仿真秒数；后续记录已改为由秒数派生帧预算。

这些是**当前交付包的已知回退风险**，不是宣称云端 v12 或服务器当前仍有相同故障。本次线上界面已能看到 v5 不具备的 Robot limits 选项和英文完整手册，也说明不能用旧源码代表当前部署。

建议：每个发布包附 `frontend_commit / worker_commit / contract_version / package_sha256 / supported_runtime / validation_receipt`；网页 Help 展示这些字段；重新导出已经验证的当前版本，保留旧包但标明历史用途。

证据：[云端当前元数据](../runs/site_audit_20261021/cloud_evidence.json)、[解包源码](../runs/site_audit_20261021/source_v5/PROJECT.md)、[工作站使用说明](../docs/site/WORKSTATION.md)。初次审阅时修复状态来自项目记录；现已按本报告顶部补充核对服务器 v13 文件。

### 2.3 场景编辑、数据生产、训练仍然是分开的流程

线上 Help 明确说明：`Sync to GPU` 只生成草稿，维护者仍要完成初态适配、可达性预检、原生采集、资格审核、动作导出、冻结缓存和登记发布。云端已有 `scene.sync` 回执也明确 `physicsValidated=false / simulationStarted=false / trainingStarted=false`。

同时，策略评估使用 `isaac32_20261017` 登记初态，界面选择同一个 room 编号，并不意味着执行了编辑器当前保存的场景版本。新数据集 ID 在 v5 的 `lib/core.ts:6` 中固定列举，不能仅靠新增服务器文件夹自动出现。

影响：用户容易将“改了场景→同步→开始训练/评估”理解为完整因果链，实际训练和评估可能仍针对原有登记数据。说明书虽然讲清楚了，主操作界面仍缺少贯穿各步的产物身份。

建议：首先在操作旁显示“草稿版本 / 实际评估初态版本 / 冻结数据集版本”，并把按钮改为清楚的“同步场景草稿”。后续再实现独立的采集与资格流水线，贯穿 draft ID、run ID、manifest SHA 和 checkpoint 输入，失败保持可见；继续保留原来的资格门，不能将预览或评估录像直接算训练来源。

证据：[完整手册第 4–5 章](../docs/site/USER_GUIDE_ZH.md)、线上 Help 第 1 章、本次云端只读作业回执；合同见解包 `lib/training.ts:34`。

### 2.4 默认数据与连接状态表达不够可靠

线上未登录进入 Data & training 时，页面显示 `Sign in with ChatGPT first` 和 `GPU snapshot`，但仍显示“Isaac · new 300 pairs：32 complete pairs”，以及只有时分秒的 `Server sample 14:33:59`。这是内置旧快照，不能当最新服务器数据；用户需要同时理解登录状态、快照与数量口径，认知成本过高。

另有 v5 静态缺陷：`app/page.tsx:25` 的周期刷新吞掉错误。`gpu.live` 是上次 bootstrap 返回的布尔值，服务器仅在请求时计算是否超过 45 秒；如果浏览器网络中断，旧的 true 不会随时间自动失效，页面可能继续显示 GPU connected。训练 ETA 也可能继续使用旧状态。这一问题尚未对云端 v12 注入断网复现。

建议：未取得认证数据前显示“示例/历史快照，日期为……”，或隐藏业务数量；全部样本时间显示日期、时区和年龄。前端独立按最后成功响应时间判断过期，并区分网站可访问、worker 心跳新鲜、模型已加载、物理帧推进四种状态。

### 2.5 异步保存可能覆盖保存期间的新编辑

v5 `app/page.tsx:39` 发出保存请求后，在响应返回时直接 `setRooms(result.rooms)` 并清除 dirty。位置输入、颜色按钮并未全部被 busy 禁用。

触发路径：用户修改 A 并保存 → 网络请求尚未返回 → 用户继续修改 B → A 的响应返回，把房间状态替换成 A 且标成 Saved。后端 revision 校验可以避免两个已提交版本冲突，但不能保护这一段尚未提交的本地 B。

这是代码路径分析，尚未使用浏览器延迟网络重现，也未核实当前线上是否已修改。建议用本地 edit sequence 与请求快照关联，响应只能确认它对应的修改；或者保存期间明确锁住全部编辑入口。验收应覆盖慢请求与“保存时继续编辑”。

### 2.6 历史查询与作业生命周期功能有限

v5 bootstrap 只查询最近 30 条作业和 12 个场景版本，前端没有分页/按 ID 检索入口。数据库保留记录不代表用户能在网页找回较旧记录。现场需要追踪某次评估时，容易重新依赖服务器路径。

API 和页面也未提供完整的取消排队、受控停止、重试派生关系。对于耗时训练和仿真，这属于管理功能缺口。建议优先实现只取消尚未领取的任务，再设计运行中任务的安全停止协议与实际退出回执；不要以改一个状态字段代替停止成功。

证据：解包 `app/api/bootstrap/route.ts:5`、`app/api/jobs/route.ts:6`、`app/page.tsx` 的 Run history。该判断限已审阅导出源码，不推断服务器没有任何人工运维手段。

### 2.7 文档、测试和证据随项目迁移不完整

本轮针对 README、docs/INDEX 和 docs/site 的 Markdown 本地链接做文件存在性检查：**117 处中 18 处目标在当前工作树不存在**，包含源码入口、历史运行报告和部分汇报产物。此检查不覆盖所有文档、标题锚点或服务器路径，也不代表目标从所有机器永久丢失。

导出源码的 10 项 Node 合同测试通过；4 项 worker 测试在 Windows 默认编码下均在 fixture 读取阶段报错，使用非 base Python `-X utf8` 后全部通过。仓库级 pytest 尚未运行：所选非 base 环境没有 pytest；同时两份 studio 测试引用的 backend 路径在当前工作树确实不存在。

建议：提供精简的证据索引与可获取位置，不必把所有大视频入 Git；给当前源码补齐与发布相关的集成验证。优先覆盖构建包完整性、断连状态、保存竞态、重复 worker/重启领取、下载与权限边界，而不是仅增加解析器单测数量。
