# MuJoCo 90/10 与 Isaac mix：MSE、闭环失败和速度诊断

核验日期：2026-10-22。范围：服务器已有模型、冻结数据、运行日志和轨迹的只读审计；新增 CPU 数值统计，没有重训、重新控制机器人、修改约束或改写历史标签。服务器证据根目录 `/home/michelle/haoze/r1pro-airport-sim/runs`。JSON 元数据同步在 [本轮证据目录](../runs/mse_rootcause_20261022/)，视频、轨迹和权重留服务器。

## 结论

**目前不能把失败归为“Isaac 模型训练坏了”。已确认有训练范围与评测起点不一致、训练标签与运行约束冲突，以及运行模式造成的速度损失；新模型自身也存在 Pick 预测退化。**

| 优先级 | 已确认的问题 | 对当前现象的解释 | 尚不能证明的部分 |
|---|---|---|---|
| P0 | Isaac 300 个 Pick 训练片段全部从教师接近托盘之后开始；网页从此前的原生初态启动 | 模型被要求补做 Isaac 训练片段未覆盖的接近动作 | 修齐起点后是否就能成功，须闭环对照 |
| P0 | 真机 Pick 训练标签有 4,984 / 13,431 帧至少一侧 joint4 低于当前登记下限 | 模型可能学会真实示范中存在、当前仿真却会截断的动作 | 登记范围、资产机械范围、真机现行参数谁需要修正，尚无现行真机配置证明 |
| P1 | 新 mix 的真实 Test Pick 历史 MSE 比旧 90/10 高约 13%，第一步高约 26% | 确有预测退化；腕部与长时域误差值得关注 | 配比、数据范围、采样和引擎同时变了，无法单独归因引擎或网络 |
| P1 | 最新运行使用 baseline：31.25 秒仿真耗时 236.53 秒 | 物理步进与同步等待推理占主要时间 | 更换模式、减少开销后达到实时仍未证明 |

旧 90/10 和新 Isaac 模型都曾在同一类 Isaac 网页入口跑到 120 秒仍未通过 Pick。结合用户的旧模型真机成功反馈，**当前仿真入口与任务分布本身必须先排查，不能仅凭仿真失败决定重新训练。** 两次运行初始相机哈希不同，不是严格固定随机性的一对一因果试验。

## 1. 从 MSE 看：退化存在，但不是训练崩溃的证据

### 1.1 与用户确认的旧模型比较

来源：旧 `real_sim_pickplace_20261009_v3/mse_mixed_pi05.json` 与新 `real_isaac300_timeweighted_pi05_20261017_v1/mse_parallel_real50_duration_bc.json`，本轮已从服务器读取，收录在 [inventory.json](../runs/mse_rootcause_20261022/inventory.json)。

两份报告均为相同真实 Test 的 19 个 episode；Pick 11 个、Place 8 个。历史协议每 5 帧取一个观测、预测 H20，剔除末尾补齐目标，底盘不计入。Pick 525 次推理、10,070 个有效目标向量。手臂是 14 个关节的均方误差，单位 rad²；夹爪是两侧开口的 mm²，不能把两者直接相加。

| Pick 指标 | 旧 MuJoCo 90/10 | 新 Isaac 50/50 | 变化 |
|---|---:|---:|---:|
| H20 手臂 MSE，rad² | 0.00846284 | 0.00958686 | +13.28% |
| 对应手臂 RMSE | 5.27° | 5.61° | +0.34° |
| 第一预测步手臂 MSE，rad² | 0.00249892 | 0.00314382 | +25.81% |
| H20 夹爪 MSE，mm² | 184.52 | 210.77 | +14.23% |
| 对应夹爪 RMSE，mm | 13.58 | 14.51 | +0.93 mm |

这两份历史报告没有本轮统一重跑成同噪声的配对实验，也没有多种子置信区间。百分比是报告值之差，不是统计显著性结论。不能把它们与网页 stride=1 的 MSE 混在同一比较中。

Place 单独报告：手臂 MSE 0.00163562 → 0.00170003，夹爪 MSE 806.03 → 649.21 mm²。Place 的夹爪改善不能抵消用户关心的 Pick 退化。

### 1.2 网页统一协议的独立交叉检查

已有任务 `amse_c9c6f69c3fa6b0bd34dde0b2` 使用 `real_all_frames_h20_noise42000_v1`：每帧推理、同观测共同噪声、相同有效目标掩码。它比较的是**新 Isaac final 与纯真机模型**，没有旧 90/10，不能冒充旧新配对。

| Pick 指标 | 纯真机 | 新 Isaac final |
|---|---:|---:|
| H20 手臂 MSE，rad² | 0.00871836 | 0.00935059 |
| H20 夹爪 MSE，mm² | 231.62 | 214.13 |

本轮重新读取服务器已保存的预测 NPZ，逐时间步计算新模型 Pick 手臂 MSE：第 1 步 0.00313185、第 5 步 0.00519907、第 10 步 0.00867540、第 20 步 0.01769168。各步有效样本数不同，依次 2,600 / 2,556 / 2,501 / 2,391；这是时域误差描述，不是控制实验。第 20 步 RMSE 约 7.62°，不能假定整个 H20 都同样可靠。

新模型 Pick 的右臂 joint5 / joint7 MSE 分别约 0.03274 / 0.03298 rad²，单关节 RMSE 约 10.4°，大于 joint4 的约 0.00855 rad²。**误差不只集中在越限肘关节；仅修 joint4 限制不保证解决抓姿。**

额外零动作基线：在同一真实 Test Pick 上，将当前测量关节保持不动，第一步 MSE 为 0.00220702，H20 为 0.01666763。新模型 H20 好于保持基线，但第一步差于保持基线。因此“小的一步 MSE”本身不是动作推进能力或成功率。

训练 loss 约 0.0033 是训练空间中的损失，不等于上述物理单位 MSE，更不等于闭环成功。离线 MSE 代码不经过运行时 filter；所以新模型**原始 MSE 变差不是 filter 在计算时造成的**。

证据：[数值重算](../runs/mse_rootcause_20261022/audit.json)、[基线与源片段核验](../runs/mse_rootcause_20261022/validation.json)、[MSE 实现](../scripts/studio_mse.py)。

## 2. 最明确的训练 / 评测不一致：接近动作没有进入 Isaac Pick 训练片段

核查 300 个 Isaac Pick 来源：导出的起点在原生轨迹第 **59–70 帧**，中位数 66 帧，即前 **2.95–3.50 秒**未进入 Pick 训练片段；每个片段只保留随后的 60 帧 / 3 秒。

代表样本 `isaacsim_parallel_pickplace300_20261017_v1/batch_000/native/rooms/room_000`：

- 教师在第 0–64 帧完成准备与双臂接近。
- Pick 导出第 64–124 帧，Place 导出第 124–184 帧。
- 该教师 Pick 有实际相对长边接触和抬升 0.1119 m，说明这条教师轨迹在原生物理中能成功；不能等同模型从原始初态也会成功。

代码链路清楚：`DiversePickPlace.prepare_pick()` 将双臂移到抓取位置上方并保持；之后 `pick()` 才开始计时。导出取 `span.start:span.end`，缓存保留这一裁剪。网页 `run_policy_room()` 则直接从原生初态调用模型，没有教师接近阶段。

数值交叉验证：网页 Room000 起点距所有 18,000 个 Isaac Pick 训练状态中最近的一帧，14 关节 RMSE 仍为 **0.6697 rad / 38.37°**；距最近片段起点 0.6777 rad。与真实 Pick 训练状态最近距离是 0.1593 rad。此距离不是全任务 OOD 分类器，但足以证实起点关节分布显著不同。

300 对样本全部属于同一个 `parent_scene_id=airport_0004_20270920` 的变化采样，不能称为 300 个独立父场景的泛化覆盖。

**判断：当前 Isaac 数据训练的是“已接近后的抓起”，网页要求的是“从更早姿态接近并抓起”。这是已证实的范围错配；它对失败的因果贡献仍需匹配初态的诊断实验来量化。** 不应偷偷加入 IK / 教师接近来提高纯模型成功率。

证据：[全部来源起点统计与服务器 v17 源码](../runs/mse_rootcause_20261022/validation.json)、[距离统计](../runs/mse_rootcause_20261022/detail.json)、[缓存构建](../r1pro_teleop/vla/parallel_pickplace_training.py)、[导出逻辑](../scripts/export_isaac_parallel_pickplace.py)。

## 3. 关节限制确实有冲突；filter 有明显干预，不能简单取消

当前登记与场景机械范围：左右 `arm_joint4` 下限 −1.7453 rad，约 −100°。真实 Pick 训练 action 标签最低 −2.0944 rad，约 −120°。

| 真机 Pick 标签 | 左 joint4 越出当前范围 | 右 joint4 越出当前范围 | 分母 |
|---|---:|---:|---:|
| Train | 2,042 帧，15.20% | 3,184 帧，23.71% | 13,431 帧 |
| Test | 261 帧，10.04% | 678 帧，26.08% | 2,600 帧 |

Train 两侧取并集为 **4,984 帧 / 37.11%**。标签与当前下限最大差约 0.3491 rad / 20°。仅要求预测严格落在当前位置边界，真实 Test Pick H20 标签就存在约 0.00073667 rad² 的不可消除最小手臂 MSE；尚未计入速度约束。

这不是已证明真机机械能到 −120°：这里只验证了数据中的动作标签。可能是仿真资产范围过窄、旧部署配置不同、动作命令允许超出反馈范围，或接口/标定语义需要对齐。必须对照成功那次真机的现行配置和实际反馈确认。**不能拿训练标签直接放宽机械范围。**

Isaac 新数据的 18,000 帧 Pick action 均在当前位置范围内；相邻动作最大速度约 1.500001 rad/s（float32 精度），与 1.5 rad/s 名义限制一致。因此“Isaac 专家数据完全没有限位”不符合检查结果。真实 Pick 数据则有 224 / 13,371 个有效相邻转换超过当前 1.5 rad/s，训练与运行还存在速率差异。

本轮检查实际模型输出与 filter 日志：

| 运行 | 含手臂位置裁剪的 H20 块 | 执行帧触发手臂速率过滤 | 实际双侧接触子步 |
|---|---:|---:|---:|
| 新 Isaac，最新 Room009，625 帧 | 42 / 125 | 89 / 625 | 0 / 15,625 |
| 新 Isaac，Room000，2,400 帧 | 134 / 241 | 614 / 2,400 | 0 / 60,000 |
| 旧 MuJoCo 90/10，Room000，2,400 帧 | 198 / 241 | 617 / 2,400 | 0 / 60,000 |

H20 块统计包含未执行的未来预测，不能直接当成执行帧裁剪率。最新运行某个预测关节最大位置修正 0.49465 rad，执行时速率过滤最大修正 0.33431 rad；不是全部可以忽略的数值微调。

最新运行托盘最大升高约 1.50 cm，但没有同时达到双侧手指各 >0.5 N 的接触；两次 120 秒运行同样没有该双侧接触。当前失败不只是最终成功标签苛刻，而是尚未建立合格的双臂抓持。

Filter 算法仍是必要的保护：20 Hz 下每帧上限 `min(0.1, 1.5×0.05)=0.075 rad`，物理层再插值为 25 个子步。之前 v17 的范围/速度验证不等于模型任务验证。当前缺的是**训练分布、部署动作合同与真实机械配置的一致性**。

另发现证据字段易误用：`native_trace.npz.raw_action` 在 `tick()` 中也被写成过滤后的 command，与 `action` 相同。二者之差为零不能证明 filter 没干预；本报告使用服务端 `checkpoint_limit_events.jsonl` 和执行端 `events.jsonl` 重算。建议后续修正字段命名或存入真正原始命令，不修改旧轨迹。

夹爪另列：真实 Pick 标签没有 >80 mm；真实 Place Train 有 2,350 / 5,422 帧 >80 mm，旧 MuJoCo Pick 有 1,513 / 2,243 帧 >80 mm。这个冲突影响混合训练和 Place，但不能把真实 Pick 的问题简单归为夹爪标签超限。

证据：[缓存及接触审计](../runs/mse_rootcause_20261022/audit.json)、[真实过滤事件统计](../runs/mse_rootcause_20261022/detail.json)、[filter 实现](../r1pro_teleop/real2sim/robot_action_filter.py)、[之前的验证边界](ROBOT_ACTION_FILTER_REVIEW_20261021.md)。

## 5. 为什么慢，确认是不是 Isaac Sim

2026-10-22后续源码核查补充：下文约0.445秒来自同一日志中的模型服务与通信层耗时混合聚合，不能解释为纯GPU前向耗时。125个模型块对应250条耗时记录；原始数值保留，计时口径与优化顺序见[专项分析](INFERENCE_SPEED_ANALYSIS_20261022.md)。本节原生物理/等待分项不受此日志混合问题影响。

最新任务 `aa89d912-2f68-4d6a-a75f-9c1f433271a5` 的配置与身份回执确认：**NVIDIA Isaac Sim / PhysX、GPU1、baseline 模式、物理 dt=0.002 s，每个 20 Hz 控制帧执行 25 个子步**。MuJoCo 在共享代码中用于私有运动学/模型结构，不是这个运行的物理步进引擎。

该任务由用户停止，已经执行 625 帧 / 15,625 个物理子步：

| 时间项 | 秒 | 对 236.53 秒原生阶段的比例 |
|---|---:|---:|
| 物理步进 `physics_step` | 137.79 | 58.25% |
| 等待推理 `planning_wait` | 56.09 | 23.71% |
| 接触读取 `contact_read` | 9.56 | 4.04% |
| 动作后渲染 `post_render` | 13.10 | 5.54% |
| 原生阶段总计 | 236.53 | 100% |

仿真时长 31.25 秒，实时系数 **0.132**，即约 **慢 7.57 倍**；整个作业含启动耗时 266.31 秒。`physics_contacts=150.24 s` 已包含物理步进和接触读取，不能再次与上述分项相加。未列出部分包括控制、状态/文件操作等开销。

单次推理日志延迟约 0.445 秒，而每次消费 5 帧只推进 0.25 秒仿真。baseline 同步等待必然增加墙钟耗时；即使完全消掉推理等待，现有 GPU 物理步进本身仍慢于实时。增大 duration 只允许跑更久，不会提升速度。

已有 realtime 模式 Room000 运行：新模型 120 秒仿真 / 218.88 秒原生阶段，实时系数 0.548；旧模型 120 / 221.08 = 0.543。它们使用 CPU PhysX 和异步推理，依然是 Isaac Sim，仍慢于实时。与最新运行不是相同房间/版本的严格测速，不能把全部倍率差归给单个开关。此前同模型、同 Room000 的短程 baseline/realtime 比较约加速 3.34 倍，见 [既有运行比较](../apps/scene-agent/public/help/runtime-comparison.json)。

**性能建议：先对同一模型、同一房间、同一预算复测已有 realtime 路径；随后分别优化子步接触读取、状态同步和日志写入。** 不建议在没有接触回归前减少 500 Hz 子步，也不建议以增加执行块长度来掩盖长时域预测误差。当前短时 GPU 空闲快照无法反推历史瓶颈或持续显存争用。

证据：[作业报告与请求](../runs/mse_rootcause_20261022/probe.json)、[引擎和设备回执](../runs/mse_rootcause_20261022/detail.json)。

## 6. 建议的修复与验证顺序

1. **先核准真实动作合同。** 取成功那次 90/10 部署的 joint4、夹爪、速率、控制频率及反馈定义，与当前资产逐项比对。明确 −100° 和 −120° 差异来源，再决定修资产、映射还是训练合同；不自行放宽机械范围。
2. **把评测起点与训练范围对齐，先做诊断。** 在初始化阶段使用冻结示范中“准备完成”的物理状态，比较旧/新模型的 Pick；标明只测抓起片段、不计完整流程。若此时表现显著改善，支持接近阶段缺失是主要原因。不能在运行中用教师/IK 帮模型接近后仍报纯模型成功。
3. **若目标是网页当前完整起点，补足接近数据。** 优先核验原生来源已保存的前 59–70 帧及其视频/状态对齐，构建新的版本，包含接近→抓取→抬升；保留旧冻结数据和检查点。此项改变训练片段范围，需要按项目规则确认方案后实施。
4. **补旧 90/10 的统一配对 MSE。** 与新模型使用同一真实 Test19、共同噪声和有效掩码，分 Pick/Place、关节、预测步报告；另在匹配的 Isaac 教师观测上做 MSE，区分“新数据都拟合不好”与“离线能拟合但上线偏移”。本轮没有新增 GPU 推理，所以该缺口仍在。
5. **最后做训练消融。** 在数据范围和动作合同一致后，比较同初始化下 90/10 与 50/50；另列从成功 90/10 续训的方案，避免一次改配比、初始化、采样和动作范围。用新运行目录，不覆盖成功模型。
6. **独立推进性能优化。** 先复测现有 realtime，再按计时优化；性能与任务成功分别验收。

当前最有价值的下一步是 **动作合同核验 + 匹配准备后起点的诊断**。直接关闭 filter、加大训练步数或把 duration 拉到 10000 秒，都不能消除已证实的起点和约束冲突。
