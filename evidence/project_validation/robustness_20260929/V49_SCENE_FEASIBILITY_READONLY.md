# V49 scene-feasibility audit (read only)

Date: 2026-09-30. This audit does not change `resources/scenes/formal`, a collection, controller code, or any v36 result. The fixed 400 are an evaluation set, not a pool from which failures may be replaced and then credited as controller wins.

## Evidence and estimand

Joined `resources/scenes/formal/manifest.json` and each formal `scene.json` to the 220 terminal failures in `evidence/project_validation/robustness_20260929/v36_failure_context_snapshot.json` by `scene_id`. The latter is the server v36 budget-closed, at-most-three-attempt experiment (`releases/robust_v36_20260929/runs/completion_full400_retry3`); its independent audit reports 842 attempts, 400 unique scenes, 180 completed. A missing failure-context row was counted as a completed scene only after checking the audit's 180 completion count. Thus the table describes v36 on the frozen old formal scenes, not candidate scenes.

Overall: 180/400 = 45.0% completed; 130 coupled-place IK failures, 32 contact handoff failures, 19 multiple-trays-lifted failures. All 130 coupled-place IK failures are ordinary and have front_count 1–3 (24/46/60); 57 are temporary-buffer placements and 73 are final placements. The target slots and temporary-buffer candidate policy are controller-fixed, so changing initial tray XY/yaw alone is not established as a cure. The `v36_coupled_ik_audit.json` reports these 130 as zero-motion place-plan failures after arrival; 18 original arrival bases were screened per case and none qualified. A scene-level static grasp check before any motion cannot reproduce that post-transport state.

The aisle gap is a poor observed separator: mean gap is 1.512 m for completed cases, 1.509 m for coupled-place IK failures, and 1.507 m for contact handoff failures. These are descriptive means, not causal tests. The strong front-count association is partly structural: front_count 0/1/2/3 changes both initial clutter and required transport/temporary-buffer work. Reweighting toward front_count 0 would change the defined task mix and is excluded. Complex cases are 20/400, all currently fail; a new feasibility rule that merely avoids stacked layouts would erase the complex challenge. `resample_count` mostly reflects the generator's static packing rejection, not demonstrated control feasibility (292 accepted at attempt 0).

The current generator in `r1pro_teleop/airport_scenes.py` fixes `front_count=index%4`, complex blocks 0/21/42/88/99, and uses `SeedSequence([seed, attempt])` for reproducible candidate sampling. It accepts static support, overlap, 3 mm penetration, and settled-velocity constraints, with at most 250 attempts per index. This is valid initial-state screening. It does not test bilateral grasp, destination release, support-preserving stack separation, the state after transport, or completion. The formal manifest records 1,767 ordinary-overlap and 294 center-of-mass-outside-table rejections before its 400 accepted scenes; an expensive controller rollout on every raw candidate would waste work and risk exceeding the current generation budget.

## Proposed new-version preflight, with explicit limits

This would be an opt-in **new scene-source version** and a separate collection/run directory. Do not edit the old 400 or their JSON/XML hashes. Preserve exactly 380 ordinary and 20 complex, exactly 100 scenes at each front_count, the complex block schedule, three trays/slots, 300/50/50 prepared split counts, table/tray contact physics, cameras, scene IDs' index-to-front-count relationship, and all existing initial-state guards. Keep the original 1–2 m gap and pose/yaw support. Record each candidate attempt, seed, rejection stage/reason, CPU time, and source hashes. Split is frozen after accepted scene IDs; preflight tuning must use development indices only and never inspect validation/test task outcomes to set thresholds.

1. **Static tier after existing physics settle (cheap).** Validate full tray footprint/support margin and neighboring rim access at initial state, clear candidate base footprints in the aisle, and a nominal final-slot and buffer footprint for each tray/slot mapping. Use the actual rotated tray hulls and existing collision geometry. These are necessary-condition screens only: all three destination slots are fixed and equally reachable across scene resamples, and a proposed buffer still requires an actual support/contact path. Reject only provably impossible layouts; ambiguous cases pass onward. Avoid simply excluding a fixed front-count or complex stratum.
2. **Isolated kinematic tier (bounded, no physics outcome label).** For the controller's finite candidate bases, test bilateral pregrasp/contact IK and collision/wrist-camera clearance at the sampled initial state; for each proposed final and temporary destination, test a small set of independent bilateral endpoint and release poses using the same geometric limits as the production controller. Require at least one *qualified* candidate for each necessary step, but treat an unreachable provisional state as `unknown`, not rejection, because real handoff/transport can alter pose. Bound to e.g. 8 scene resamples and 24 base/pose probes per surviving candidate initially; these numbers are experimental budgets, not evidence of adequate coverage. Use no actual release motion or successful-rollout signal to rank candidates.
3. **Physical validation tier only after source freeze.** Prepare/preflight the new collection, then run budget-closed full MuJoCo episodes with actual contact dynamics and native cameras. A preflight acceptance is never `task_completed`. The new source should get its own identifier, manifest, spec revision, rejection report, and full400 attempt-level summary; old v36 remains untouched.

The kinematic tier can only support a claim about geometric feasibility under the frozen controller. It cannot pre-certify contact handoff, stacked separation, carried-tray support, or end-to-end success. For the 19 complex multiple-trays-lifted cases, static support-chain inspection can identify stacked geometry but cannot establish whether the top tray separates under closed-loop contact forces; filtering all stacks would violate the retained complex distribution. Likewise, 57/130 IK failures involve a controller-selected temporary destination: a scene generator cannot guarantee these go away without changing that controller policy or observing its reached state.

## Validation and decision gate

First implement the preflight only as a dry-run audit on old400 plus separately generated *unregistered* candidates. Measure rejection reasons and time per candidate by difficulty/front_count, false-negative rate on the 180 known completed old scenes, and whether it flags known failures within each stratum. A rule that rejects completed old scenes, collapses front_count 2/3, or simply rejects every stack is unsuitable. Perform ablations (`static`, `static+IK`) and retain unknown/abstention counts. Sample and inspect a handful of rejected candidates physically before trusting the geometric criterion. Bound total generation time, and fail visibly if a stratum cannot fill its quota within 250 original attempts; never silently replace it with easier strata.

Then freeze the rule before generating an independent new formal400, preserve the seed/attempt provenance and split, and run the exact same v36 controller/config with the same three-attempt stopping budget in fresh run directories. Report both per-stratum and overall completion, first-attempt and budget-closed completion, failure classes, attempts, generation cost, and video evidence. Compare against the frozen old400 only as **different scene distributions**. To demonstrate a controller improvement, evaluate the changed controller on the *same* old400 (and ideally the new400) with unchanged acceptance. A 70% rate on newly filtered scenes, if achieved, means 70% for that declared feasible-source version; it does not retroactively make v36 280/400 on the old collection.

Current evidence gives no calibrated probability that this preflight will reach 70%. The 130 destination-side coupled IK failures and 20/20 complex failures are serious blockers. Their mechanisms point more directly to controller destination/support planning than to raw generator rejection. This audit recommends a measured dry-run before implementation or new-scene claims.

## Offline classifier diagnostic on the *old* fixed400

`scene_feasibility_offline.py` predeclares three static screens before reading outcome labels: flag a scene if `front_count >= 1`, `>= 2`, or `>= 3`, respectively, **or** if any tray's `support_parent` is another tray. These thresholds are deliberately simple geometry/crowding proxies. The script reads only existing scene JSON, the 220 terminal failure-context entries, and the existing coupled-IK audit; it executes no MuJoCo episode and edits no collection. It writes the full per-difficulty/front-count matrices, failure-code coverage, and historical-success scene IDs to `V49_SCENE_FEASIBILITY_OFFLINE.json`. `TP` means an old failure flagged; `FP` means an old success would be rejected; `TN` means an old success retained; `FN` means an old failure retained. This is diagnostic classification on the same old400, not a predictive validation on new scenes.

| Predeclared static screen | TP/FP/TN/FN | Historical successes wrongly rejected | Coupled IK flagged | Multiple-trays-lifted flagged |
|---|---:|---:|---:|---:|
| front_count ≥1 or stack | 214 / 91 / 89 / 6 | 91/180 | 130/130 | 19/19 |
| front_count ≥2 or stack | 168 / 42 / 138 / 52 | 42/180 | 106/130 | 19/19 |
| front_count ≥3 or stack | 91 / 24 / 156 / 129 | 24/180 | 60/130 | 19/19 |

The apparent ability to flag every stacked failure is tautological: the stack branch flags **all 20 complex scenes**, including the one whose terminal code was not multiple-trays-lifted. That is not a useful feasibility rule because it would remove the complex task itself. Similarly, the front-count thresholds classify entire fixed strata and cannot discriminate success from failure *within* front_count 1/2/3. For example, the middle variant rejects all 95 ordinary front_count-2 scenes, including 18 historical successes, and all 95 ordinary front_count-3 scenes, including 24 successes; it retains all front_count-1 ordinary scenes, including 46 failures. Per-stratum results in the JSON make this confounding explicit. None of these screens meets the proposed criterion to preserve difficulty and front-count distribution, and none should be used for resampling.

The local bounded **initial** reachability probe covers only scene 6; no comparable initial reachability screen exists for all 400. The existing `arrival_screen` records in `v36_coupled_ik_audit.json` cover the 130 selected coupled-IK failures, but they occur *after* transport and are selected by failure type. Feeding their `qualified=0` signal into this classifier would leak the outcome and falsely inflate performance. The script reports this availability but does not use the signal as a feature. A legitimate next diagnostic would run an isolated, capped initial-state screen across all 400 before examining labels, then evaluate its errors within each stratum. This offline result specifically rules out simple stratum/stack exclusion as a credible shortcut to 70%.
